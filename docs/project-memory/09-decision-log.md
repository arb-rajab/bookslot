## D-0001 — Reuse Laravel + PostgreSQL, deliberately, despite this being a repeated stack

- **Date:** 2026-08-23 · **Status:** accepted
- **Context:** the public portfolio track has a governance rule pushing
  against repeating a primary backend/database across public repositories,
  to demonstrate technical range to a reviewer. This repository is private
  commercial work with no such reviewer audience, and that rule explicitly
  does not apply to private repositories.
- **Decision:** use Laravel (PHP) as the backend and PostgreSQL as the
  database, matching this developer's other proven work.
- **Why (business fitness, not laziness):** this targets a price-sensitive
  market (see `00-project-brief.md`) where delivery speed and low ongoing
  operating cost decide commercial viability. Spending build time learning
  an unfamiliar stack for this specific product would misallocate scarce
  effort away from the parts of this product that are genuinely novel and
  risky (Stripe Connect, multi-tenancy) and toward re-deriving skills
  already held. PostgreSQL is additionally justified on its own technical
  merits independent of reuse — its exclusion-constraint mechanism is a
  strong fit for the double-booking-prevention problem (see
  `03-architecture.md`).
- **Must not be silently reversed because:** if a future session proposes
  switching stacks "for variety" or "to try something new," that is
  optimizing for the wrong incentive — this is not a public portfolio piece
  being judged on range. A real reason (e.g., a genuine technical
  limitation discovered during implementation) would be needed to revisit
  this.

## D-0005 — Tenant isolation: row-level `tenant_id`, enforced at both the application layer and via Postgres RLS

- **Date:** 2026-08-24 · **Status:** accepted
- **Context:** `03-architecture.md`'s original direction was row-level `tenant_id` scoping enforced only via Laravel ORM global scopes. `06-security-threat-model.md` flags multi-tenancy as the one genuinely new architectural risk relative to this developer's other work (`privacy-forge` is single-org). App-scope-only enforcement means a raw query, a forgotten global scope, or a queued job that runs without tenant context set is a full cross-tenant data leak with no second line of defense.
- **Options considered:**
  - Row-level `tenant_id`, app-layer scoping only — simplest, but the failure mode above has unbounded blast radius (a single missed scope leaks every tenant's rows in that table).
  - **Row-level `tenant_id`, app-layer scoping + Postgres RLS backstop — chosen.**
  - Schema-per-tenant — rejected: migration ergonomics scale linearly with tenant count (every migration runs N times, schema-drift risk), cross-tenant/platform-admin reporting becomes cross-schema queries, and Laravel tooling for it (e.g. stancl/tenancy) adds real operational complexity disproportionate to a segment of many *small* (1–6 chair) tenants. Would win if the trajectory shifted to few, large, high-ACV tenants needing contractual isolation guarantees — 01's segment boundary explicitly excludes that for MVP.
  - Database-per-tenant — rejected: multiplies connection management, migration orchestration, and backup fleet per tenant with no stated compliance/data-residency requirement to justify it.
- **Decision:** every tenant-scoped table carries a `tenant_id` FK. Enforcement is two independent layers: (1) Laravel global scopes on every Eloquent model, and (2) Postgres Row-Level Security policies on every tenant-scoped table with `FORCE ROW LEVEL SECURITY`, keyed on a session GUC (`app.current_tenant_id`) set by request middleware and at the start of every queued job. If the GUC is unset, RLS matches zero rows — fail closed, not fail open. Migrations run under a separate DB role that is not subject to RLS (RLS binds the app's runtime role only). Cross-tenant/platform-admin queries go through an explicit, narrow admin role/policy (e.g. `BYPASSRLS`), not an app-code path that casually skips scopes.
- **Why:** this caps the blast radius of the entire "forgot to scope a query" bug class from "all tenants' data in that table" down to "zero rows," at the database layer, regardless of which code path issued the query — directly answering 06's flag that this is the one area where "we've done this before" doesn't apply.
- **Note on GDPR erasure (06):** 06's erasure requirement applies to a studio's *end customer*, not the tenant/studio itself — so it's a row-level concern independent of which tenancy boundary wins here. This decision doesn't change how erasure is handled; see `04-data-model.md`.
- **Must not be silently reversed because:** dropping the RLS layer back to app-scope-only would silently remove the fail-closed backstop that is the whole point of this decision — see the amendment in `03-architecture.md`.

## D-0006 — Deposit mechanics: immediate-capture PaymentIntent with saved card for the balance charge

- **Date:** 2026-08-24 · **Status:** accepted
- **Context:** three realistic mechanics exist for collecting a deposit and later a balance via Stripe Connect. This vertical's bookings are typically made weeks in advance (00's stated value proposition rests on this lead time enabling a multi-touchpoint reminder cadence).
- **Options considered:**
  - **Immediate-capture PaymentIntent at booking time, with `setup_future_usage: off_session` to save the card for the later balance charge; disposition (forfeit/apply/refund) is a later explicit action on already-captured funds — chosen.**
  - Manual-capture PaymentIntent, held and captured/cancelled at appointment time — rejected: Stripe's manual-capture authorization holds expire (commonly around 7 days, varies by network/issuer), far short of this vertical's typical multi-week booking lead time. Most real bookings would outlive the hold before the appointment happens. Would win in a shorter-lead-time vertical (e.g. short-notice bookings) — out of scope, since we're not building for verticals not yet committed to.
  - SetupIntent saving a card, charged only on no-show — rejected: no money moves at booking time, which contradicts 00's stated mechanic ("pays a deposit... so my slot is held") and removes the up-front skin-in-the-game effect the business case (R-04) credits for reducing no-shows. Also risks an off-session SCA/3-D-Secure decline at the exact moment — weeks later, no cardholder present — the studio is trying to enforce the no-show penalty. Would win only under a deliberate product repositioning of "deposit" as a pure no-show penalty rather than an upfront payment — a business decision, not an engineering one, and contradicts 00 as currently written.
- **Decision:** deposit is captured immediately at booking via a Stripe Connect destination charge (`application_fee_amount` for the platform's cut). The same PaymentIntent saves the payment method for later off-session use. Disposition after the appointment is bookkeeping on already-moved funds: attended → applied to balance (no further Stripe call); no-show → forfeited per studio policy (no further Stripe call); cancelled within a studio-configured window → an explicit refund (partial or full) of the captured charge.
- **Booking vs. payment state:** modeled as two loosely-coupled state machines (booking lifecycle; payment status per payment row), not one merged machine — a booking can be cancelled after its deposit is captured (refund is a decision independent of booking status), and a payment can be mid-flight (e.g. awaiting 3DS) independent of the booking's own lifecycle. See `04-data-model.md`.
- **Consequences to disclose (open, not yet resolved):** destination charges assign dispute/chargeback liability to the connected account (the studio) by default — correct here since the studio is merchant of record, but studio-onboarding copy (a future session) needs to disclose this explicitly rather than let it surface as a surprise at first dispute. Statement descriptor (what the customer's card statement shows) is a per-connected-account Stripe setting — open product question, not a schema blocker.
- **Must not be silently reversed because:** switching to manual-capture later would require re-deriving the hold-expiry-vs-lead-time tradeoff above; switching to SetupIntent-only would be a real repositioning of the product's deposit value proposition, not a technical tweak.

## D-0007 — Double-booking exclusion constraint: tenant+resource scoped, partial, buffer excluded from the stored range

- **Date:** 2026-08-24 · **Status:** accepted
- **Context:** `03-architecture.md` recorded the `tstzrange` + `EXCLUDE USING gist` direction but not its specifics.
- **Decision:**
  - `btree_gist` extension created in its own early migration, before any migration adding the exclusion constraint (GIST has no native `=` operator support for scalar types like `uuid` without it).
  - Constraint scoped by both `tenant_id` and `resource_id` (equality) and `appointment_range` (overlap `&&`), with a **partial** `WHERE (status NOT IN ('cancelled', 'no_show') AND deleted_at IS NULL)` — without this, a cancelled appointment's row would permanently block that slot from ever being rebooked.
  - Range bounds convention: `'[)'` (half-open), Postgres's default for `tstzrange` — a 2–3pm slot and a 3–4pm slot must not be treated as overlapping. Ranges constructed explicitly with `tstzrange(start, end, '[)')`, plus `CHECK (lower(appointment_range) < upper(appointment_range))` since `tstzrange` permits empty/backwards ranges.
  - Buffer/turnaround time is **not** baked into the stored range — the stored range is the literal appointment window only. Buffer is enforced at slot-*generation* time (computing bookable slots excludes a margin around existing appointments, per service/studio configuration), because buffer requirements are a variable business rule, not the one hard invariant (zero literal overlap) the database must guarantee.
  - Timezone/DST: `timestamptz` stores absolute instants, so the constraint's overlap comparison is DST-proof by construction. DST sensitivity exists only upstream, converting a studio-local wall-clock time to an absolute range at booking-creation time — must use the studio's stored IANA timezone with zone-aware arithmetic, not fixed-offset math.
  - Constraint-violation error surfacing: an exclusion violation raises SQLSTATE `23P01`. Booking-creation code must catch this specific code (not a generic exception catch-all) at a single chokepoint and translate it to HTTP 409 with a machine-readable code (`SLOT_ALREADY_BOOKED`), never a 500. Required concurrency test case: two simultaneous booking attempts on the same slot — one 201, one clean 409.
- **Rejected alternative:** baking buffer into the stored range — rejected because it would make `appointment_range` misrepresent the appointment's actual duration on the calendar, and buffer policy can change per service without needing different range semantics.
- **Must not be silently reversed because:** removing the partial `WHERE` clause would make cancelled slots permanently unbookable; changing the bounds convention without updating all range construction call sites would silently reintroduce boundary-adjacent double-booking bugs.

## D-0008 — Buffer enforcement moved into the exclusion constraint via a second, generated occupancy range

- **Date:** 2026-08-24 · **Status:** accepted
- **Context:** Session 3 review of D-0007 found that buffer/turnaround time, as specified ("enforced at slot-generation time... not baked into the stored range"), is unenforceable under concurrency. Slot generation is a read. The EXCLUDE constraint is the only serialization point, and it compares `appointment_range` (the literal window) with `&&`. Two concurrent requests can each compute available slots (correctly excluding a buffer margin) before either commits, then insert two appointments whose literal ranges are disjoint but whose *buffered* windows overlap — the constraint has no way to see this, because the buffer requirement was never expressed in the ranges it compares.
- **Options considered:**
  - **A second, generated `occupancy_range` column carrying the EXCLUDE constraint, with `appointment_range` staying the literal, customer-facing window — chosen.**
  - Extend `appointment_range` itself to include buffer, subtracting buffer at presentation time — rejected: this is the exact alternative D-0007 already rejected, for the same reason (`appointment_range` would misrepresent the appointment's actual duration on the calendar). Reviving it would also mean every consumer of the range (confirmation emails, calendar exports, dashboard) must remember to subtract buffer; one omission leaks buffer time into what the customer is told is their appointment.
  - Accept the race explicitly, unresolved — rejected: it is a real, if narrow, correctness gap (two customers claiming adjacent slots within the same short window) with a concrete bad outcome (an artist with no cleanup time between clients), for the one property (`03`'s "one correctness property this product cannot get wrong") the product is explicitly built around. The fix costs the same engineering effort as documenting why it's left open.
- **Decision:**
  - `appointments` gains `buffer_before_minutes integer NOT NULL DEFAULT 0` and `buffer_after_minutes integer NOT NULL DEFAULT 0`, **snapshotted from the service/studio's buffer configuration at booking-creation time** — not looked up live, and not stored as a single "buffer_minutes" value, so a studio's later buffer-config change never retroactively alters an already-created booking's occupancy window.
  - A new generated column:
    ```sql
    occupancy_range tstzrange GENERATED ALWAYS AS (
      tstzrange(
        lower(appointment_range) - (buffer_before_minutes || ' minutes')::interval,
        upper(appointment_range) + (buffer_after_minutes || ' minutes')::interval,
        '[)'
      )
    ) STORED
    ```
  - The exclusion constraint from D-0007 moves from `appointment_range WITH &&` to `occupancy_range WITH &&`, keeping the same `tenant_id WITH =`, `staff_id WITH =`, and partial `WHERE (status NOT IN ('cancelled','no_show'))` clause unchanged.
  - `appointment_range` is untouched and remains what the customer sees (confirmation, calendar, dashboard) — buffer stays entirely invisible to the customer-facing surface, exactly as D-0007 intended.
- **Why this resolves the race:** the constraint now sees the same buffered window both requests would have separately computed at read time, and enforces it transactionally at insert time — the same mechanism, and the same guarantee, D-0007 already established for literal overlap, extended to cover buffer.
- **Consequences addressed:**
  - **Variable per-artist/per-service buffer:** correct by construction — each row's constraint check uses that row's own snapshotted buffer, not a shared or live value (a generated column couldn't reference a live config table even if this weren't otherwise desirable).
  - **Studio changes its buffer with future bookings already on the books:** existing rows keep their originally-snapshotted buffer; only bookings created after the change get the new one. This is deliberate grandfathering, not a bug — no backfill/migration of existing appointments is needed or intended when a studio edits its buffer setting.
  - **Legitimate back-to-back bookings:** unaffected — a service/studio configured with `buffer_before_minutes = buffer_after_minutes = 0` makes `occupancy_range` identical to `appointment_range`, reproducing today's zero-buffer behavior exactly.
- **Open product question (not answered here):** whether MVP defaults buffer to "after only" (cleanup time following a service) versus allowing both before and after per service — the schema supports either; the default value is a product decision for a future session, not fabricated here.
- **Resolved by D-0024 (Session 7):** both before and after are configurable at MVP. See D-0024 for the ruling and why this required no schema change.
- **Must not be silently reversed because:** removing `occupancy_range` and reverting the constraint to `appointment_range` would silently reopen this exact race; changing which column carries the buffer snapshot (e.g., looking it up live instead of storing it on the row) would break the grandfathering guarantee and could make the generated column non-deterministic.

### Amendment (Session 4, 2026-08-24) — DDL corrected after execution testing: generated-column immutability failure, hardened function, containment CHECK

Session 3's DDL above was written but never executed. Executing it against PostgreSQL 17.11 fails:

```sql
ALTER TABLE appointments ADD COLUMN occupancy_range tstzrange
  GENERATED ALWAYS AS (
    tstzrange(
      lower(appointment_range) - (buffer_before_minutes || ' minutes')::interval,
      upper(appointment_range) + (buffer_after_minutes || ' minutes')::interval,
      '[)'
    )
  ) STORED;
```
```
ERROR:  generation expression is not immutable
SQLSTATE: 42P17
```
Postgres's immutability checker cannot prove the `integer || text` concatenation and `::interval` cast chain is immutable — even though it is, in this case, since none of the inputs are `now()`- or session-dependent — and refuses to create the column outright rather than merely warning.

**Options considered to fix it:**
- (a) **Trigger-maintained column** — a `BEFORE INSERT OR UPDATE` trigger computes and sets `occupancy_range` — rejected: this reintroduces the exact "did the write path actually run the trigger" trust problem generated columns exist to eliminate. A true generated column cannot be independently written by any INSERT/UPDATE; a trigger-set column can be silently bypassed or desynced by any write path that doesn't expect it, with no database-level guarantee catching the mismatch.
- (b) **A narrow, explicitly `IMMUTABLE`-marked SQL function wrapping the same arithmetic, referenced from the generated column expression — chosen.** `occupancy_window(appt tstzrange, buf_before integer, buf_after integer) RETURNS tstzrange`, declared `IMMUTABLE PARALLEL SAFE`, sidesteps Postgres's inability to *prove* immutability of the inline expression by having the function's author assert it directly — a legitimate assertion here, since the function's actual behavior never touches `now()`, wall-clock/session state, or anything else genuinely non-immutable.
- (c) **Application-layer population** — compute `occupancy_range` in Laravel and pass it explicitly on every insert — rejected: this is D-0008's originally-rejected shape by another name. The entire point of `occupancy_range` is to make the buffered window a database-enforced invariant rather than an application-remembered one; moving its computation to the app reopens the "did every write path remember to compute it correctly" trust gap generated columns were chosen specifically to close.

**Executed proof, PostgreSQL 17.11, scratch database.** The chosen function, as actually defined and confirmed via `\sf occupancy_window`:
```sql
CREATE OR REPLACE FUNCTION public.occupancy_window(appt tstzrange, buf_before integer, buf_after integer)
 RETURNS tstzrange
 LANGUAGE sql
 IMMUTABLE PARALLEL SAFE
 SET search_path TO 'pg_catalog', 'pg_temp'
AS $function$
  SELECT tstzrange(
    lower(appt) - make_interval(mins => buf_before),
    upper(appt) + make_interval(mins => buf_after),
    '[)'
  )
$function$
```
`occupancy_range tstzrange GENERATED ALWAYS AS (occupancy_window(appointment_range, buffer_before_minutes, buffer_after_minutes)) STORED` is accepted without error.

**V1 — containment CHECK, executed this session:**
```sql
ALTER TABLE appointments
  ADD CONSTRAINT appointments_occupancy_contains_appt
  CHECK (occupancy_range @> appointment_range);
```
→ `ALTER TABLE` (accepted — a CHECK constraint may reference a stored generated column at table-alteration time, same as any other column). Proven to bite: with the buffer CHECKs temporarily dropped and `buffer_before_minutes = -5` inserted (the same non-inverting case flagged as a real gap above),
```
ERROR:  new row for relation "appointments" violates check constraint "appointments_occupancy_contains_appt"
```
This CHECK is now part of the DDL in `04-data-model.md`; the buffer-bounds CHECKs remain in place alongside it — see the redundancy note there.

**V2 — inline `SET search_path`, executed this session:** the function above carries `SET search_path TO 'pg_catalog', 'pg_temp'` as part of its `CREATE FUNCTION` statement itself, not applied after the fact via a separate `ALTER FUNCTION` (which is how the previous session's hardening was demonstrated). Under a hostile session setting that explicitly repositions `pg_catalog` (`SET search_path = evil, public, pg_catalog`, with `evil.make_interval(integer)` shadowing the real one), a twin function defined identically but *without* the inline `SET search_path` clause resolves `make_interval` to the hostile schema's version and returns a garbage multi-month range (`["2026-07-21 19:00:00+00","2026-10-13 02:00:00+00")` for a 1-hour appointment with a 5-minute buffer); the production `occupancy_window`, and a freshly-built inline-hardened twin run side by side for direct comparison, both continue to return the correct `["2026-09-01 09:55:00+00","2026-09-01 11:05:00+00")`. The inline form is confirmed equivalent to the previously-demonstrated `ALTER FUNCTION ... SET search_path` form. `04`'s DDL now carries the hardening inline at `CREATE FUNCTION` time, so no migration window exists where the function is ever deployed unhardened.

**Search_path hardening — deciding reason.** The function is hardened with `SET search_path = pg_catalog, pg_temp` for **explicitness and version-independence**: name resolution inside the function is fixed at definition time regardless of whatever the calling session's `search_path` happens to be, rather than relying on Postgres's implicit-pg_catalog-first behavior continuing to hold under every possible caller configuration. This is *not* about avoiding a higher minimum-version requirement — inline `SET search_path` on `CREATE FUNCTION` is supported on every version this schema could plausibly target, so hardening vs. not hardening makes no difference to the version floor either way (see below). The attack this closes is not exotic: an operator with `ALTER ROLE ... SET search_path` or `ALTER DATABASE ... SET search_path` privilege — not an unusual grant for a migration or ops role — can reposition `pg_catalog` for any session using that role/database, at which point any *unhardened* function becomes hijackable by whatever a hostile or merely careless schema places earlier in that path. D-0005's rejected schema-per-tenant option is relevant here, not as a tie-in for its own sake: had it been chosen, routine per-tenant schema use would have made multi-schema `search_path` handling — and therefore this exact class of repositioning — a normal, frequent occurrence rather than an unusual administrative action. That is one more reason D-0005's row-level-tenancy choice was right, and one more reason this hardening is worth doing unconditionally regardless of which tenancy model had won.

**PostgreSQL version floor — pinned explicitly, not left implicit.** The floor is **PostgreSQL 12**, set by exactly one feature this schema depends on:

| Feature used in `04`'s DDL | Minimum PostgreSQL version | Binding? |
|---|---|---|
| `GENERATED ALWAYS AS (...) STORED` (generated columns) | 12 | **Yes — this is the actual floor.** |
| `EXCLUDE USING gist` + `btree_gist` on scalar equality types | 9.2 (btree_gist itself older still) | No — below the generated-column floor |
| Row-Level Security (`ENABLE`/`FORCE ROW LEVEL SECURITY`, policies) | 9.5 | No — below the generated-column floor |
| `tstzrange` / range types | 9.2 | No — below the generated-column floor |
| `gen_random_uuid()` (built-in since 13; available via `pgcrypto` on any earlier supported version) | n/a | No — `pgcrypto` covers every version back past 12 |
| Per-function `SET search_path` on `CREATE FUNCTION` | long-standing, predates every row above | No |

This belongs in `04` because below PostgreSQL 12, this schema **cannot be expressed at all** — `occupancy_range` (and `starts_at`/`ends_at`) have no fallback representation without generated columns. `08-deployment-and-operations.md`, once written, chooses the actual deployed version and hosting provider *above* this floor as an operational/cost/vendor-availability decision — a different question with a different owner than this one. **In practice this floor is non-binding:** PostgreSQL 12 reached end-of-life in November 2024, and every version any competent hosting provider offers today already clears it by multiple major versions. It is recorded anyway, honestly, because "what does this schema actually require" and "what will we actually run" are two different questions belonging to two different documents (`04` and `08` respectively) — conflating them would make a future version downgrade look safe by convention rather than because someone re-checked why 12 was the floor in the first place.

**Must not be silently reversed because:** reverting to the direct arithmetic `GENERATED ALWAYS AS` expression is not a stylistic rollback — it is unexecutable DDL (`42P17`) that fails at migration time outright, not a version that silently passes with different behavior. Removing the inline `SET search_path` (relying on a later `ALTER FUNCTION` step, or omitting it) reopens a real migration window in which the function is briefly deployed unhardened.

## D-0009 — RLS tenant-context lifecycle: transaction-scoped `SET LOCAL`, named roles, and impersonation-based admin access

- **Date:** 2026-08-24 · **Status:** accepted
- **Context:** D-0005 established *that* Postgres RLS backstops tenant isolation, keyed on a session GUC (`app.current_tenant_id`), but not *when or how* that GUC is set and cleared. `SET LOCAL`/`set_config(..., true)` only resets at `COMMIT`/`ROLLBACK` — on a pooled or long-lived connection (Horizon workers, PgBouncer), an ambient session-level `SET` would leak the previous request's or job's tenant to whoever reuses that connection next. This needed an explicit lifecycle, not an assumed one.
- **Decision:**
  - **Mechanism:** the tenant GUC is always set via a parameterized `set_config('app.current_tenant_id', ?, true)` call (never a string-interpolated `SET LOCAL ...`, which would be a SQL-injection vector), as the first statement inside an explicitly opened database transaction. This is the only mechanism used anywhere in the system — there is no session-level fallback.
  - **HTTP requests:** every tenant-scoped request (reads included) runs inside a transaction opened by a `SetTenantContext` middleware, which resolves `tenant_id`, sets the GUC, invokes the handler, and commits (or rolls back on exception). Wrapping reads in a transaction is the cost accepted for the GUC-reset guarantee to hold unconditionally, rather than depending on cleanup code running.
  - **Queue workers (Horizon):** the same shape via a `TenantScopedJob` base class — `tenant_id` is a required constructor argument (a job that doesn't extend this base, or omits it, cannot be dispatched), and a job-level queue middleware opens a transaction, sets the GUC from the job's own serialized `tenant_id`, runs `handle()`, and commits/rolls back. Because the GUC is transaction-scoped, a job can never inherit a prior job's tenant on a reused worker connection, *provided every tenant-touching job extends this base* — enforcing that is a test-suite concern (`07-testing-strategy.md`), not a runtime one.
    - **Retries** re-run `handle()` from the same serialized payload, so `tenant_id` is re-supplied automatically; a custom `__serialize`/`__wakeup` override that strips it is the one way this could silently break.
    - **Batches** may span tenants (e.g., a platform-wide rebooking-prompt sweep) as long as each job in the batch sets its own context independently — the batch mechanism itself carries no ambient tenant assumption.
    - **Tenant-less platform jobs** (e.g., purging `stripe_webhook_events`) use a separate `PlatformJob` base that sets no tenant GUC and is restricted to non-tenant-scoped tables.
  - **Connection pooling:** PgBouncer **transaction mode** is compatible and preferred, not merely tolerated — it reclaims a backend connection at the same `COMMIT`/`ROLLBACK` boundary where the GUC already resets, so the two lifecycles line up exactly. Session mode also works. What is incompatible: anything that promotes `SET LOCAL` to a session-level `SET`, or any connection-reuse behavior that spans a transaction boundary without a matching reset. Recorded as a forward constraint on `08-deployment-and-operations.md`'s eventual hosting/pooling choice, not resolved here.
  - **Roles:**
    - `bookslot_app` — the sole runtime role (HTTP and queue workers both authenticate as this). Ordinary role, fully subject to RLS, never granted `BYPASSRLS`.
    - `bookslot_migrator` — owns the tables and holds `BYPASSRLS`. Used only by migrations, seeders, backfills, and `pg_dump`/`pg_restore` — all offline, human- or CI-triggered, never reachable from a running request. Uses separate `.env`-configured credentials from `bookslot_app`, so the two can never be interchanged by configuration error.
    - **No separate live-request bypass role** — see the admin-path decision below.
  - **Platform-admin cross-tenant path:** the admin endpoint (`GET /api/admin/tenants/{id}/appointments`) authenticates as the ordinary `bookslot_app` role and sets `app.current_tenant_id` to the specific `{id}` being inspected — identical to any normal tenant-scoped request — gated by an app-layer check that the caller is `role = 'platform_admin'`. This **revises D-0005's "(e.g., `BYPASSRLS`)" parenthetical** for the live admin path specifically: `BYPASSRLS` remains reserved for `bookslot_migrator`'s offline use only. Rejected alternative: a literal `BYPASSRLS` role used live by the admin endpoint — simpler, but a bug in the admin authorization check combined with a live `BYPASSRLS` role reproduces the exact full-cross-tenant-leak failure mode RLS exists to prevent (worst case: every tenant's data, gated by one check). The impersonation approach keeps RLS fail-closed even for the admin path itself — worst case of an authz bug there is exposure of one wrong tenant, not all of them. There is now exactly one RLS-bypass surface in the whole system, and it is never reachable from a live request.
  - **Unauthenticated public booking path:** the client supplies only a `slug` (a deliberately public, shareable identifier — the booking-page URL itself). The server resolves `slug → tenant_id` via a parameterized lookup against `tenants` (outside the RLS boundary per `04`), and only that server-resolved value is passed to `set_config()` — never anything from the request body. A customer-supplied `tenant_id` anywhere in a public request payload is ignored server-side in favor of the slug-resolved value; this is not an injection vector because the client never controls the value that reaches the GUC. The manage-booking-link path (`GET /api/bookings/manage/{token}`) instead derives trust from the signed token itself.
- **Must not be silently reversed because:** switching any tenant-scoped code path to session-level `SET` instead of transaction-scoped `set_config(..., true)` reintroduces the cross-request/cross-job leak this decision exists to close; granting `BYPASSRLS` to a live-request role would collapse the admin-path guarantee back to the rejected alternative above.

**Extended by D-0021 (Session 7):** this decision's public-path tenant-resolution list was originally two concrete instances (slug-based; the one manage-booking token). D-0021 found a third public endpoint (`POST /api/bookings/{id}/confirm-payment`) that fit neither, and closed the gap by generalizing the *token* half of this decision into a reusable mechanism class — a signed, purpose-scoped, tenant-carrying token — rather than inventing a third, unrelated mechanism. This decision's own text is otherwise unchanged; see D-0021 for the generalization and its reasoning.

## D-0012 — Buffer has no default: required, explicit input at service creation (amends D-0008)

- **Date:** 2026-08-24 · **Status:** accepted
- **Context:** D-0008's DDL (as corrected in Session 4) declares `buffer_before_minutes integer NOT NULL DEFAULT 0` and `buffer_after_minutes integer NOT NULL DEFAULT 0` on `appointments`, snapshotted from "the service/studio's buffer configuration" — but no such configuration column was ever actually added anywhere in `04-data-model.md`; the snapshot source didn't exist. This ruling closes both gaps at once: it decides the default-value question D-0008 explicitly left open, and it supplies the missing configuration field the snapshot mechanism was already assuming.
- **Options considered:**
  - Default to zero — rejected. A studio owner who doesn't think about buffer at service-creation time silently gets back-to-back appointments with zero turnaround for needle disposal, station breakdown, or sterilization. That is a real operational hazard for this vertical specifically (00's tattoo-studio framing), not a hypothetical edge case, and a silent zero-by-inattention default is the worst way to arrive at it.
  - A provisional non-zero default (e.g. 15 minutes) — rejected. Any non-zero number invented here would be exactly the kind of business-policy guess `00`'s business assumptions section is careful not to fabricate — turnaround time genuinely varies by service (a small flash tattoo vs. a multi-hour custom piece) and by studio, and a platform-wide guessed default would be wrong for most services most of the time in a way that's worse than forcing the choice.
  - **No default — buffer is a required field the owner must set explicitly when creating a service, for both `buffer_before_minutes` and `buffer_after_minutes` — chosen.**
- **Decision:**
  - `services` gains `buffer_before_minutes integer NOT NULL` and `buffer_after_minutes integer NOT NULL` (no `DEFAULT` clause — an `INSERT` that omits either column fails, rather than silently getting zero), with the same `CHECK (... >= 0 AND ... <= 1440)` bounds already established for `appointments`' snapshot columns in D-0008.
  - `appointments.buffer_before_minutes` / `buffer_after_minutes` remain `NOT NULL` but lose the `DEFAULT 0` clause — they are always populated explicitly by application code from the owning service's (now-required) buffer configuration at booking-creation time, per D-0008's snapshot rule; removing the column default is a statement of intent (this value is never meant to arrive by omission) even though the application, not a bare `INSERT`, is the only real write path.
  - This does not decide D-0008's separate, still-open question of whether MVP restricts buffer to "after only" or allows both before and after per service — both columns exist either way; a studio is free to set either to `0` explicitly (an informed zero, not an inattentive one) if it wants back-to-back scheduling for a given service.
- **Why this is authorization/onboarding-flow reasoning, not just a schema tweak:** per `01`'s non-paternalism framing (the product doesn't silently decide business policy on a studio's behalf — see the parallel reasoning for no-show disposition, FR-08), the right response to "we don't know the correct number" is to make the owner choose deliberately, not to have the platform guess quietly on their behalf. Forcing an explicit choice at the one moment (service creation) the owner is already thinking about that service's specifics is the cheapest point to ask.
- **Not made this session:** the actual UI/copy prompting the owner for this value, and `05-api-contracts.md`'s `POST/PATCH /api/owner/services` request/response shapes reflecting the new required fields — `05` was not in this session's authorized scope for this ruling (only D-0008 and `04` were named); adding the fields to `05` is a small, low-risk follow-up left as an open item rather than done here without being asked.
- **Must not be silently reversed because:** reintroducing a numeric `DEFAULT` on either `services` column would silently reopen the zero-by-inattention hazard this ruling exists to close.

### Postscript (Session 6, 2026-08-24) — what this gap says about the verification, not just the fix

D-0012 fixed a real bug: D-0008's "snapshotted from the service/studio's
buffer configuration" language assumed a source column that was never
actually added anywhere in `04-data-model.md` until this ruling supplied
it. That means D-0008's snapshot-at-booking semantics — the actual property
D-0008 exists to provide, that a studio changing its buffer later never
retroactively alters an already-created booking's occupancy window — were
unimplementable as written for four sessions (Sessions 3 through this
gap's discovery). During that entire span, the DDL executed without error,
the exclusion constraint behaved correctly against every case tested, and
nothing in the process caught it.

**Why not:** every test and every execution check across those sessions
asked a version of "is the schema internally consistent" — does the DDL run,
does the constraint reject an overlapping insert, does the containment CHECK
hold, does `occupancy_window()` resist a hostile `search_path`. None of them
asked "does changing a studio's buffer configuration actually leave existing
bookings' `occupancy_range` values unchanged and give new bookings the new
value" — the literal guarantee D-0008's own text describes as its purpose.
A schema can be perfectly self-consistent while the specific property it was
introduced to deliver was never exercised at all, because self-consistency
and delivering-the-stated-property are different claims that happen to look
identical until the second one is actually tested. See `07-testing-strategy.md`'s
new buffer-config-change case (added Session 6) — the direct fix for this
class of gap, not just for this one instance of it.

## D-0020 — `bookslot_migrator` credential stays out of the automated deploy pipeline (refines D-0009)

- **Date:** 2026-08-24 · **Status:** accepted
- **Context:** D-0009 named `bookslot_migrator` (holds `BYPASSRLS`) as used only "offline, human- or CI-triggered" — treating those two as roughly equivalent, since both are "never reachable from a running request." Writing `08-deployment-and-operations.md` forced a more honest look at that equivalence: if migrations run automatically as part of an automated CI/CD deploy pipeline, the migrator's `BYPASSRLS`-capable credential must live as a CI secret, reachable by every pipeline run — a materially larger and more automatable attack surface (a compromised pipeline config, a malicious PR touching CI YAML, a compromised third-party Action) than a credential a human deliberately fetches for one manual invocation. D-0009's "human- or CI-triggered" phrasing didn't distinguish these, and this decision does.
- **Options considered:**
  - Migrator credential lives in the CI/CD pipeline's secret store, migrations run automatically on every deploy — rejected as the default: this is the single `BYPASSRLS`-capable credential in the entire system (D-0009), and putting it inside the same automated system that runs on every merge (with its larger, more automatable, and more supply-chain-exposed surface) trades away most of the "never reachable from a live/automated path" property D-0009 was designed around, for the convenience of not having a manual release step.
  - **Migrations run as a separate, manually-triggered step outside the automatic deploy path — chosen.** A human operator runs the migration explicitly (e.g., from a secured bastion/operator session, using a migrator credential fetched just-in-time from a secrets manager for that one invocation, or via a CI job gated behind a required manual approval that only that gated job — never the general build — can read the credential for), before the corresponding application version is promoted.
- **Decision:** `bookslot_migrator`'s credential is never stored as a general CI/CD secret reachable by ordinary pipeline runs. Migrations are a deliberate, human-gated step in the release process, not an automatic consequence of merging to `main`.
- **Cost, stated plainly, not papered over:** this gives up a fully automated merge-to-production pipeline. Every release that includes a migration requires a human to explicitly run it, in the right order relative to the application deploy (see `08-deployment-and-operations.md`'s migration-safety section) — an extra manual step that must be remembered and done correctly under whatever time pressure a release carries, which is itself a real (if smaller and more contained) risk this decision accepts in exchange for keeping the `BYPASSRLS` surface out of the larger automated system.
- **Must not be silently reversed because:** adding `bookslot_migrator` to general CI secrets "just for convenience" on some future deploy-automation push would quietly undo the entire point of this decision — the blast-radius argument above would need to be re-examined and explicitly overridden, not bypassed by a config change nobody thought was a security decision.

## D-0021 — Confirm-payment tenant context: a booking-scoped signed token replaces the raw appointment ID (amends D-0009)

- **Date:** 2026-08-24 · **Status:** accepted
- **Context:** Session 6's contradiction audit found that `POST /api/bookings/{id}/confirm-payment` is public, unauthenticated, and keyed only by a bare, unscoped `appointment_id` — matching neither of D-0009's two named public-path tenant-resolution mechanisms (slug-based; the manage-booking signed token). This is not a documentation gap: an honest implementation that never sets `app.current_tenant_id` from unauthenticated input has no way to resolve tenant context from a bare ID at all, since the row that would tell it the tenant is itself RLS-protected — a chicken-and-egg deadlock, not a bug fixable by being careful. The realistic way an implementer "fixes" that deadlock is to resolve `tenant_id` from `appointment_id` via an unscoped lookup (a raw query, or reaching for the `bookslot_migrator`/`BYPASSRLS` role for "just this one lookup") — which reopens exactly the live, unauthenticated-request `BYPASSRLS` exposure D-0020 was written to prevent, and, short of that, lets anyone holding a real `appointment_id` (obtained by disclosure — a forwarded email, shared-device browser history, a URL-logging pipeline — not brute force, since D-0007/`04` already uses `uuid`, not sequential integers) query and interact with another tenant's booking/payment state. UUID entropy raises the bar from trivial to "requires disclosure of one real ID," but does not close the hole, because the ID was never meant to function as a credential in the first place.
- **Options considered:**
  - **A booking-scoped, purpose-scoped signed token, generalizing D-0009's existing manage-booking token mechanism rather than inventing a third one — chosen.**
  - Derive tenant context from the Stripe PaymentIntent (retrieve the PI server-side, read tenant_id from its metadata) — rejected as the default: adds a synchronous external Stripe call, and a new failure mode (Stripe unreachable), to the customer-facing deposit-confirmation hot path, and creates a new invariant to maintain forever (PI metadata must always carry a correct `tenant_id` and never be stripped by any code path that touches the PaymentIntent). Would win if a future session finds Stripe-metadata-as-source-of-truth is needed for another reason — not needed to close this specific gap.
  - Make the endpoint authenticated — rejected: contradicts `02-requirements.md`'s actor model (customers have no account relationship with bookslot at all). A session-cookie variant is a bearer credential by another name and, unlike a token, does not survive a customer switching devices mid-checkout (a real J1/J2 scenario).
  - Remove the endpoint; rely on Stripe webhooks alone — rejected: contradicts `04-data-model.md`'s own booking-state-machine narrative (confirmation is synchronous on the no-3DS path, per J1 step 5) and the precedent `05-api-contracts.md` endpoint 6 (`balance/charge`) already set — a synchronous, actionable `200` response for a payment outcome the client needs to render UI around, not a webhook-only side channel the client has no way to observe directly. Revisiting that UX pattern is a real redesign, out of this session's authorized scope.
- **Decision:**
  - `POST /api/tenants/{slug}/bookings`'s `201` response gains a new field, `payment_confirmation_token` — **deliberately distinct from `manage_token`**, not a reuse of it. Least-privilege reasoning: `manage_token` is scoped to viewing/cancelling a booking; a leaked `manage_token` must not also grant the ability to drive payment confirmation/retry, which is a materially more sensitive action on a money-carrying path.
  - The endpoint's route changes from `POST /api/bookings/{id}/confirm-payment` to **`POST /api/bookings/{token}/confirm-payment`** — the token is the sole path identifier; a raw, client-supplied `appointment_id` no longer appears anywhere in this endpoint's contract.
  - The token is a signed (same signing infrastructure as `manage_token` — no new signing scheme introduced), stateless capability carrying `tenant_id`, `appointment_id`, `purpose = "confirm_payment"`, `issued_at`, and an `expires_at` claim set to booking-creation time plus the hold-window configuration value (D-0011) plus a small fixed grace period — an independent, defense-in-depth expiry that holds even if the hold-window-enforcement job itself fails to run.
  - **Verification order, strictly:** (1) verify the token's signature, `purpose`, and `expires_at` before anything else — a bad signature, wrong purpose (e.g., a `manage_token` presented here), or expired token is rejected with a generic `404 { "error": "INVALID_OR_EXPIRED_TOKEN" }` that reveals nothing about whether any appointment exists (there is no separate raw ID in the request to leak against); (2) only once verified, set `app.current_tenant_id` from the token's own signed (trusted) `tenant_id` — never from any other input; (3) perform the RLS-protected read/write against the token's `appointment_id`.
  - **Not single-use.** Valid for repeated calls while the appointment's `status = pending_payment`, supporting J2's retry-with-a-different-card flow. Once the appointment leaves `pending_payment`, further calls are idempotent status echoes (`{"status":"confirmed"}`) or the existing `409 BOOKING_EXPIRED`, never a fresh mutation — the same idempotency discipline J9 already established for webhook delivery, now also gated on token validity.
  - **No new storage.** Like `manage_token`, this is a stateless signed capability verified by signature alone, not a stored, revocable row — `04-data-model.md` needs no schema change for this decision. (Recorded explicitly since this session was instructed to touch `04` only if storage were required.)
  - **This generalizes, rather than replaces, D-0009's token mechanism:** D-0009's framing of "exactly two public-path mechanisms" (slug; one specific token) is revised to "slug-based, and a signed-token capability class," of which the manage-booking token and this new payment-confirmation token are two distinct, purpose-scoped instances. A future public endpoint needing tenant context should default to a third instance of this same class rather than reopening this question. See the pointer added to D-0009 above.
- **Consequences for other endpoints, raised rather than acted on:** none of `05`'s other public endpoints need a change — the manage-booking-link endpoints already fit the (now-generalized) mechanism as-is. No owner/staff/admin endpoint is affected; this decision is confined to one public, unauthenticated endpoint.
- **Must not be silently reversed because:** reverting the route to accept a raw `appointment_id` again reopens the exact hole this decision closes; reusing `manage_token` for this purpose instead of a distinct token would silently widen what a leaked manage-booking link can do.

## D-0022 — Erasure carve-out for `payment_mandates`: retained in full, including `accepted_ip`/`accepted_user_agent`, on a legal-claims basis

- **Date:** 2026-08-24 · **Status:** accepted
- **Context:** `07-testing-strategy.md`'s Session 6 amendment flagged a real, unresolved gap: whether/how a customer erasure (FR-18) interacts with that customer's `payment_mandates` rows — which carry `accepted_ip` (arguably personal data) — was unspecified anywhere in `04-data-model.md`. `payment_mandates` has no direct customer-identifying column (no `customer_id`, no name/email/phone) — it links only via `appointment_id`; the actual identifying fields (`customers.name`/`email`/`phone`) are already nulled in place by `04`'s existing erasure handling, unchanged by this decision. What was actually undecided is narrower and specific: does erasure touch `payment_mandates` at all, and specifically its `accepted_ip`/`accepted_user_agent` columns.
- **Ruling (given):** mandate evidence is retained after customer erasure — this is a deliberate carve-out from `06`'s general erasure handling, not a conflict with it, because mandates are dispute evidence: erasing them would destroy the ability to defend a chargeback for a transaction that legitimately occurred, and privacy regimes generally permit retention on a legal-claims basis (an explicit statutory exception to erasure in comparable regimes — e.g. GDPR Art. 17(3)(e)-equivalent "for the establishment, exercise or defence of legal claims" — not an invented workaround).
- **Decision, precise per-column:**
  - `payment_mandates` is **never modified or deleted** by a customer erasure, in full — every column survives exactly as recorded at accept-time: `mandate_text`, `mandate_template_version`, `balance_amount_disclosed`, `accepted_at`, `stripe_payment_intent_id`, `stripe_payment_method_id`, and (see below) `accepted_ip`/`accepted_user_agent`.
  - **`accepted_ip` and `accepted_user_agent` are classified as evidentiary, not identifying, and are retained.** Their retained value is narrow and specific: corroborating, at a future dispute, that the accept-time request came from a plausible, consistent session/device/geography — exactly the forensic purpose Stripe-dispute defense turns on. This is a different purpose from `customers.name`/`email`/`phone`, whose only function is identifying/contacting the person; nulling IP/user-agent would gut the one purpose this table exists for (dispute defense) while doing nothing `customers`' own anonymization doesn't already accomplish for the "stop identifying this person" purpose. General data-protection classification of IP as personal data does not change this: retention here is justified per-purpose (legal-claims/dispute-evidence), not by reclassifying IP as non-personal.
  - `customers.name`/`email`/`phone` continue to be nulled in place exactly as `04`'s existing Soft delete matrix already specifies — this decision does not change that.
  - `appointments` and `booking_events` are unaffected (already true per `04`'s existing matrix) — both remain linked via `appointment_id`, so a mandate stays reconstructable alongside its booking's audit trail after the linked customer's erasure.
- **Why this is a carve-out, not a conflict, stated for `06`:** `06`'s GDPR-erasure-equivalent control is about a studio's own end customer's identifying data — it was never meant to reach evidence of an already-completed, legitimate transaction that the business (and bookslot, as processor) has an independent, recognized legal basis to retain. Recording the carve-out explicitly in `06` prevents a future session from reading `06`'s erasure language as requiring `payment_mandates` to be touched.
- **Must not be silently reversed because:** nulling `accepted_ip`/`accepted_user_agent` (or deleting `payment_mandates` rows) on a future "more privacy-conservative" pass would silently destroy the specific dispute-defense value D-0010 built this table for, without being asked to trade that value away.

## D-0025 — RLS fail-closed comparison hardened with NULLIF: `current_setting()` returns `''`, not NULL, once a connection has ever set the GUC (amends D-0005/D-0009)

- **Date:** 2026-08-24 · **Status:** accepted
- **Context:** D-0005's RLS design, and `04-data-model.md`'s tenancy-boundary DDL, both state that `current_setting('app.current_tenant_id', true)` returns `NULL` when the GUC is unset, so an unset context compares as `tenant_id = NULL` (no match, fail closed) rather than erroring. This session (the first to actually execute the schema against real workloads, not just single ad-hoc statements) found that claim is only true for a physical connection that has **never** called `set_config()` for this GUC at all. Once any transaction on a given connection has set it — even once, even successfully committed — Postgres treats the custom GUC as permanently defined for that connection's remaining session lifetime: every later transaction that doesn't set it gets `current_setting(..., true) = ''` (empty string), not `NULL`, including after a real `COMMIT` (not only across nested savepoints). Verified directly against PostgreSQL 17.11:
  ```sql
  BEGIN;
  SELECT set_config('app.current_tenant_id', 'abc-123', true);
  COMMIT;
  SELECT current_setting('app.current_tenant_id', true) IS NULL;  -- false
  -- a later, unrelated transaction on the SAME connection:
  BEGIN;
  SELECT current_setting('app.current_tenant_id', true) IS NULL;  -- still false
  COMMIT;
  ```
  Since every tenant-scoped RLS policy casts this value (`tenant_id = current_setting(...)::uuid`), an empty string raises `SQLSTATE 22P02` ("invalid input syntax for type uuid") rather than comparing as `NULL`. This is not an obscure edge case for this project specifically: `08-deployment-and-operations.md`'s chosen posture is PgBouncer **transaction-mode pooling**, which deliberately reuses physical connections across many requests/tenants — meaning this "GUC permanently defined, unset now means empty string" state is the normal condition on every backend connection after its first tenant-scoped transaction, not a rare cold-start case.
- **Why this matters, precisely:** it doesn't create a cross-tenant data leak — an errored query returns no rows either, same as the documented zero-rows outcome. What it changes is *how* a missing-context bug on a reused connection would actually surface: a thrown exception (`22P02`), not the silent, gracefully-empty result D-0005/`04` describe. Depending on how calling code handles database exceptions, that could mean a `500` instead of an empty list for a real bug — a reliability/UX difference, not a security one, but a real divergence from the documented mechanism that a future session debugging "why did this query throw" would otherwise have no record of.
- **Options considered (presented to the user before proceeding):**
  - **Wrap the comparison in `NULLIF(current_setting(guc, true), '')` before the `::uuid` cast, on every tenant-scoped RLS policy — chosen.** Treats an empty string exactly like NULL again, restoring the documented fail-closed-to-zero-rows behavior for real, verified directly against Postgres 17.11 both before and after the change. Mechanical, faithful to D-0005's actual stated intent, no behavior change for the already-correct "never touched" case.
  - Leave the DDL as `04` originally specified and treat the resulting exception as an acceptable (if undocumented) form of fail-closed — rejected: it would leave `04`'s own text making a claim about the running system that isn't true, and "the guarantee still holds, just via a different, unhandled failure mode" isn't something a future session should have to rediscover by hitting a `500` in production.
- **Decision:** every `CREATE POLICY tenant_isolation` statement (including `users`' widened platform-admin policy) uses `tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid` instead of the un-guarded cast. No other part of D-0005/D-0009's mechanism changes — `set_config()` is still always parameterized, still always `is_local = true`, still always the first statement inside an explicitly opened transaction (`App\Tenancy\TenantContext`).
- **Consequence for testing infrastructure:** proving "fails closed with no context set" inside a single Pest test (which needs real fixture rows to already exist, created via an earlier `TenantContext::run()` call in the *same* RefreshDatabase-wrapped transaction) requires an explicit clear — `TenantContext::clear()` calls `set_config(guc, NULL, true)`, which itself resets to `''` per the finding above, now correctly treated as unset by the hardened policies. A fresh, never-touched connection was never a realistic thing to reproduce inside one continuous test transaction anyway.
- **Must not be silently reversed because:** removing the `NULLIF(...)` wrapper reopens the exact gap this decision closes — on any connection that has ever set a real tenant context (which, under this project's own chosen pooling strategy, is the normal state), a future missing-context bug would throw `22P02` instead of failing closed the way `04`'s own text says it does.

## D-0026 — SignedTenantToken: D-0009/D-0021's token class implemented via Laravel's Crypt facade, url-safe base64-wrapped

- **Date:** 2026-08-24 · **Status:** accepted
- **Context:** D-0009 named a signed-token public-path mechanism; D-0021 generalized it into a reusable "capability class" (`manage_booking`, `confirm_payment`, and any future purpose) but explicitly deferred the concrete implementation — neither decision specifies what signs the token or how it's encoded for transport. This session is the first to actually build a route that needs one.
- **Options considered:**
  - **`Crypt::encryptString()`/`decryptString()` (Laravel's own AES-256-CBC + HMAC, keyed on `APP_KEY`) over a JSON payload, then base64url-wrapped for safe use as a single URL path segment — chosen.** Reuses infrastructure the framework already provides and every environment already configures (no new secret to provision or rotate beyond `APP_KEY`, which every Laravel app already has); the HMAC gives tamper-evidence for free, satisfying D-0021's "signed" requirement without introducing a second signing scheme.
  - Laravel's `URL::temporarySignedRoute()` / signed-URL middleware — rejected: designed for signing an entire URL (query-string based, verified against the exact route/params), not for minting a portable, purpose-scoped, self-contained token value that travels as a single path segment across two different endpoints (`manage_booking` for one route, `confirm_payment` for another) — the two don't have the same shape need.
  - A JWT library — rejected: adds a new dependency and a new signing/verification surface for something Laravel's own `Crypt` facade already does adequately (encryption inherently includes tamper-evidence here since decryption fails on modification), for no benefit this project's scope calls for.
- **Decision:** `App\Tenancy\SignedTenantToken::issue(purpose, tenantId, appointmentId, ?expiresAt)` builds a JSON envelope (`purpose`, `tenant_id`, `appointment_id`, `issued_at`, `expires_at`), encrypts it via `Crypt::encryptString()`, and re-encodes the result as base64url (`+/=` → `-_`, padding stripped) so it is safe to embed directly in a route path segment. `::verify(token, expectedPurpose)` reverses this, and — deliberately, per D-0021's own reasoning — collapses every failure mode (bad signature, corrupted/non-base64 input, wrong `purpose`, expired `expires_at`) into one `InvalidTenantTokenException`, caught broadly (`catch (Throwable)`) at this specific attacker-facing input boundary rather than the narrower catches used elsewhere in this codebase — an explicit, scoped exception to this project's general avoid-defensive-code discipline, justified because this is the one boundary parsing caller-supplied, potentially-adversarial input. No new storage: verification is signature-and-claims only, matching D-0021's "no new storage" decision exactly — nothing here required a `04-data-model.md` change.
- **Must not be silently reversed because:** switching to a different signing mechanism later without updating every already-issued token's verification path would break in-flight tokens (a customer mid-checkout with an already-emailed link); introducing a second signing scheme per purpose (rather than one class, many purposes) would silently fragment D-0021's "one capability class" decision back into the "third mechanism" shape D-0021 explicitly avoided.

## D-0027 — Stripe-mid-request transaction boundary: raised, not decided (a gap in D-0009, surfaced by this session's wiring, not yet resolved)

- **Date:** 2026-08-24 · **Status:** raised, not decided
- **Context:** D-0009's `SetTenantContext` middleware wraps a tenant-scoped HTTP request's *entire* handler in one database transaction — resolve tenant, `set_config(...)`, invoke the handler, commit or roll back on exception. Every controller this session builds is pure-DB (no Stripe call), so that shape is exercised correctly and is not wrong for what exists today. It becomes wrong the moment a future controller must call Stripe mid-request — concretely, the still-unbuilt `POST /api/tenants/{slug}/bookings` (creates a `pending_payment` appointment, then a Stripe PaymentIntent, synchronously, per J1/D-0006). Holding that request's entire DB transaction open across a slow or unreliable external HTTP call: (1) works directly against the reason this project runs PgBouncer in transaction mode (`08-deployment-and-operations.md`) — the backend connection is held for the external call's full duration, not released back to the pool; (2) holds whatever locks the transaction has acquired (relevant here: `appointments`' GIST exclusion index, freshly written to by the same request) for that same duration; and (3) couples the DB commit to Stripe's own success/failure in a way that's easy to get wrong — a Stripe call that succeeds, followed by an unrelated exception later in the same request, rolls back the very appointment row the customer's card was just charged against.
- **Proposed boundary, not built this session (no Stripe-touching controller exists to build it against):** a route whose flow needs an external call should not rely on the blanket "wrap the whole request" shape at all. Instead, its controller should call `TenantContext::run()` itself, more than once, explicitly: one short transaction to do the tenant-scoped DB work up to the point an external call is needed (e.g., insert the `pending_payment` row, commit), the Stripe call made *outside* any open transaction, then a second short transaction (re-opening tenant context) to record the result. `SetTenantContext`'s current whole-request-transaction shape stays correct and unmodified for every pure-DB route (including every controller this session adds) — this is a per-route choice, not a change to the middleware itself.
- **Why raised rather than decided here:** D-0009 already exists and this session's mandate is to wire it as documented, not redesign it; no controller built this session touches Stripe, so nothing in this session's actual code depends on resolving this either way. Deciding it now, with no real Stripe-touching route to validate the proposal against, risks the same "designed but never executed" gap D-0008's own history (`09`'s D-0012 postscript) already shows this project's process is alert to.
- **Must not be silently resolved by whoever builds the booking-creation endpoint just picking one:** the choice affects money-carrying correctness (a charged customer with a rolled-back appointment, or an open transaction held across an external call) — it should be a deliberate ruling, informed by whatever Stripe integration approach that future session actually takes, not an incidental side effect of how the controller happens to get written.

## D-0029 — Owner/staff/platform_admin auth: Sanctum SPA (stateful/cookie) mode, one shared `web` guard, role-based authorization at the app layer

- **Date:** 2026-08-25 · **Status:** accepted
- **Context:** `05-api-contracts.md`'s Deferred section has listed owner/staff/admin auth token mechanics (session vs. API token) as undecided since Session 2; Session 9 confirmed this actually blocks building any authenticated controller, not just a documentation gap. This session's ruling: Laravel Sanctum, SPA (stateful/cookie) mode, one guard shared by all three roles, role-based authorization at the app layer matching D-0009's existing `role = 'platform_admin'` pattern — not a separate guard per role.
- **What Sanctum actually contributes, and what it doesn't:** per Sanctum's own documented SPA pattern, authentication itself stays Laravel's ordinary `web` session guard (`config/auth.php`, unchanged) — Sanctum's *only* job here is `EnsureFrontendRequestsAreStateful` (prepended to the `api` middleware group), which makes a request from a configured `SANCTUM_STATEFUL_DOMAINS` origin carry the session + CSRF middleware group instead of being treated as stateless. No `personal_access_tokens` table, no `auth:sanctum` guard, no bearer tokens anywhere — this is a pure cookie/session design, so publishing Sanctum's token migration was deliberately skipped as unneeded schema.
- **The chicken-and-egg problem building this surfaced, and how it's resolved:** `users` is both RLS- and app-scope-protected, and `users_tenant_email_unique` is scoped *per tenant* (the same email can legitimately belong to two different studios' owners) — so an owner/staff login lookup has no way to know which tenant's row to check without already knowing the tenant, the same shape of problem D-0021 solved for `confirm-payment`. Resolved the same way D-0009's existing mechanisms already do it, rather than inventing a credential-bearing scheme: **`POST /api/tenants/{slug}/login`** runs behind the existing slug-resolution middleware (`resolve.tenant.slug` + `tenant.context`) exactly like every other tenant-scoped public route, so the credential lookup is already correctly scoped by both enforcement layers before `Auth::attempt()` ever runs. A `platform_admin` row has `tenant_id NULL` by design and is visible with **no** tenant context at all — both `UserTenantScope` (app layer) and the widened `users` RLS policy special-case `role = 'platform_admin'` to be visible unconditionally (Session 8/`04`) — so **`POST /api/admin/login`** needs no tenant-resolution step and is a separate route for that reason, not an arbitrary duplication. Each login method additionally rejects (logs out, `401`) a credential match of the wrong role for that entry point, so the two routes stay meaningfully distinct rather than merely cosmetically so.
- **Four `resolve.tenant.*` mechanisms now exist, not two:** D-0009's original slug-based and signed-token (D-0021) mechanisms are joined by two new ones this session enables: `resolve.tenant.from-user` (owner/staff — tenant context is a property of who's authenticated, read from the user's own `tenant_id`, never client input) and `resolve.tenant.impersonate` (platform_admin — D-0009's impersonation path, tenant resolved from the route's own `{tenant}` parameter, reachable only after `role:platform_admin` has already run). Ordering, enforced per route group in `routes/api.php`: public → `resolve.tenant.slug|token` → `tenant.context`; owner/staff → `auth` → `role:owner,staff` → `resolve.tenant.from-user` → `tenant.context`; platform-admin → `auth` → `role:platform_admin` → `resolve.tenant.impersonate` → `tenant.context`.
- **Role-based authorization (`App\Http\Middleware\EnsureRole`, alias `role:<comma-separated-roles>`):** reads `$request->user()->role` after `auth` has already run — never a second authentication step, never a second guard. This is the literal "one guard, role-checked at the app layer" shape the ruling asked for, and mirrors D-0009's own `role = 'platform_admin'` check for the admin path rather than introducing a different authorization pattern for owner/staff.
- **CORS/session infra needed for real cross-origin cookies:** `config/cors.php` (newly published — none existed before this session) sets `supports_credentials = true` and an explicit `FRONTEND_URLS`-driven origin allowlist (never `'*'`, which browsers reject outright once credentials are involved and which would defeat an allowlist's purpose anyway) — the decoupled Nuxt frontend (`03-architecture.md`) is a different origin from this API. `SESSION_DRIVER` moves from `array` to `redis` in `.env`/`.env.example` (already provisioned for cache/queue) for real deployments, since Sanctum SPA auth needs a session that actually persists across requests; `.env.testing` deliberately keeps `array` (see the test-only reasoning below).
- **Proven with a real CSRF-rejection test, not assumed from framework defaults:** Laravel's own CSRF middleware (`PreventRequestForgery::runningUnitTests()`) unconditionally skips CSRF verification whenever `app()->runningInConsole() && app()->runningUnitTests()` — both true for every ordinary Pest run. Confirmed by removing the workaround and watching the "rejected" test actually flip to a `200` before restoring it — a naive test written against this framework default would have proven nothing. `tests/Support/AuthTestHelpers.php`'s `disableConsoleCsrfBypass()` forces `runningInConsole()` to `false` via reflection (there is no public API for this) for the specific tests that need to exercise the real check, so the CSRF test in `AuthControllerTest.php` exercises the same code path a real browser request would hit.
- **What got built and gated this session, concretely (not every owner/staff/admin endpoint `05` lists — a representative, real slice of each):** `POST /api/owner/services` (owner, D-0012's already-fully-specified shape), `GET /api/staff/appointments` (staff, FR-16/D-0013 own-bookings-only — proven by a real test that a second staff member's appointments in the same tenant never appear), `GET /api/admin/tenants/{tenant}/appointments` (platform_admin, D-0009's impersonation path — proven by a real test that impersonating tenant A never leaks tenant B's rows). The rest of `05`'s owner/staff/admin endpoint rows remain unbuilt, same as before this session, but are now unblocked rather than blocked on an undecided auth mechanism.
- **Not built, raised rather than invented:** per-route rate limiting on the new login endpoints (brute-force protection) and password-reset/account-provisioning flows — neither was named by this ruling, and inventing either now would be exactly the kind of unasked-for scope this project's discipline avoids. Left as an open item.
- **Must not be silently reversed because:** switching either login route to a bearer-token/API-token scheme would reintroduce the "which guard" ambiguity this decision exists to settle; moving role checks into a second guard per role would silently fragment the "one shared guard" property this decision explicitly chose over that alternative.

## D-0032 — D-0031 reconfirmed against the deferred-row alternative; backfill silent-failure gap recorded as R-07

- **Date:** 2026-08-25 · **Status:** accepted
- **Context:** a clarification request asked whether D-0031 had actually considered deferring the whole `payment_mandates` row to confirm-payment time (keeping `stripe_payment_method_id NOT NULL`), rather than creating an intentionally-incomplete row and backfilling it — and, separately, whether anything catches a backfill that never completes. D-0031's own text already lists and rejects this alternative ("move the whole `payment_mandates` insert to confirm-payment time... rejected"); this entry redoes that comparison explicitly against D-0010's evidentiary purpose rather than relying on D-0031's one-line rejection, and checks the monitoring question against the actual codebase rather than assuming.
- **Comparison, redone:**
  - **Deferred-row alternative:** capturing `accepted_at`/`accepted_ip`/`accepted_user_agent` only once a payment method is confirmed would either (a) record the *wrong* moment — confirmation time, potentially a different device/network than the one that actually clicked consent, which is an evidentiary defect, not just a delay — or (b) require holding the real consent evidence (rendered mandate text, disclosed balance, true timestamp/IP/UA) somewhere less durable and less audited than a committed row (session, cache, queued job payload) until confirm-payment finally runs, which is the exact same "might never complete" risk D-0031 exists to describe, only relocated somewhere less visible. If confirm-payment never runs at all (abandoned checkout), this alternative leaves **zero record** that the customer agreed to anything — strictly worse than a row with one null column.
  - **Nullable-with-backfill (D-0031, unchanged):** the row exists from the actual moment of consent, with every field that constitutes the evidentiary core — `mandate_text`, `balance_amount_disclosed`, `accepted_at`, `accepted_ip`, `accepted_user_agent`, `stripe_payment_intent_id` — captured atomically and correctly regardless of what happens afterward. Only `stripe_payment_method_id` (which future charge target) can be missing, and only in scenarios where no future off-session charge is even possible: either the deposit itself was never confirmed (no payment method was ever attached at Stripe; no off-session charge, no dispute over one, can occur) or the deposit succeeded and a payment method exists at Stripe but the write-back into this column never ran.
  - **Verdict:** D-0031 stands. Nullable-with-backfill dominates the deferred-row alternative on the exact axis D-0010 was built for (evidentiary completeness of *consent*), and is no worse on the axis the alternative claims to protect (the charge-target field), since that axis is equally unrecoverable under either design if a write-back step is skipped or never reached.
- **The real, confirmed gap:** the second failure mode above — deposit succeeds, Stripe has a payment method, but the code that writes it into `payment_mandates.stripe_payment_method_id` never runs (bug, webhook delivery failure, downtime) — is currently silent. Checked directly, not assumed: `app/Console` contains no scheduled jobs at all as of this session, and no reconciliation logic against `payment_mandates` exists anywhere in the codebase. If a dispute later arrives for that appointment's off-session balance charge — the exact scenario D-0010 exists to defend — the mandate-evidence record would be present but silently missing the field identifying which payment method it covers.
- **Decision:** record this as its own risk-register entry, **R-07** (`10-risk-register.md`), rather than leaving it as an implicit reading of D-0031's "not built this session" line. Recommended mitigation (not built this session, since this session's scope is the clarification itself, not new feature work): a reconciliation check — scheduled job or nightly query — flagging any `payment_mandates` row with `stripe_payment_intent_id` set and `stripe_payment_method_id` still null past a short grace window, built alongside the backfill code itself, not as a separate later pass.
- **Must not be silently reversed because:** treating R-07 as already covered by D-0031's "needs building" item would conflate two different facts — that the backfill code doesn't exist yet, and that nothing would notice if it existed and silently failed. The first is a known TODO; the second is the actual risk this entry exists to track.

## D-0041 — Public booking endpoints still require Sanctum's CSRF cookie; the frontend performs the real cookie dance rather than the backend exempting them

- **Date:** 2026-08-26 · **Status:** accepted
- **Context:** found by executing a real cross-origin `POST` against the running API with `Origin: http://localhost:3000` (this session's own CORS verification step), not by reading the code: D-0029's Sanctum SPA (stateful/cookie) mode applies `EnsureFrontendRequestsAreStateful`'s session + CSRF middleware group to **every** `/api/*` request from a configured stateful origin, regardless of whether that route is authenticated. `POST /api/tenants/{slug}/bookings` — a public, unauthenticated, customer-facing endpoint — returned `419 CSRF token mismatch` the first time it was actually called from the frontend's own origin, since no prior request had primed the `XSRF-TOKEN` cookie. This had never been exercised before this session because no frontend origin, and no real cross-origin HTTP client, had ever called any endpoint in this project until now.
- **Options considered:** (a) exempt the public booking/confirm-payment/login routes from CSRF verification (`VerifyCsrfToken::$except` or a route-group-level bypass), treating CSRF as an authenticated-only concern; (b) leave CSRF protection exactly as D-0029 built it (uniform per-origin, not per-auth-state) and have the frontend perform Sanctum's own documented SPA pattern — `GET /sanctum/csrf-cookie` once, then echo the resulting cookie back as an `X-XSRF-TOKEN` header on every state-changing request.
- **Decision: (b).** CSRF protection here defends against a malicious third-party site silently submitting requests using a victim's browser session/cookies for *this origin* — a risk that exists for an unauthenticated public form exactly as much as an authenticated one (a forged booking, submitted using a real customer's browser without their knowledge, is a real abuse case, not a hypothetical one). Exempting the public routes would narrow this project's own CSRF coverage for a UX convenience the frontend can provide for free — `ofetch`/`$fetch` just doesn't do this automatically the way `axios` does, so it needed to be done explicitly, not skipped.
- **Built:** `frontend/app/composables/useApi.ts`'s `apiFetch()` calls `ensureCsrfCookie()` (memoized per browser session, `GET {apiOrigin}/sanctum/csrf-cookie`, client-only — SSR's own server-side `GET` calls never mutate state and are exempt from CSRF by Laravel's own default, so they need no token) before any non-`GET`/`HEAD` request, then reads the `XSRF-TOKEN` cookie directly (`document.cookie`, URL-decoded) and sends it as `X-XSRF-TOKEN`.

## D-0043 — Owner/staff auth: session-based tenant resolution replaces the unreachable `auth`-before-`tenant.context` ordering (amends D-0029)

- **Date:** 2026-08-26 · **Status:** accepted
- **Context:** building D-0042's endpoints and testing them for real against a live `php artisan serve` process (not just Pest) surfaced a serious, previously-undetected bug: **a returning owner/staff session could never re-authenticate on any request after the first.** D-0029's original owner/staff middleware order was `auth -> role:owner,staff -> resolve.tenant.from-user -> tenant.context` — `resolve.tenant.from-user` read `$request->user()->tenant_id`, which presupposes `auth` already resolved the user. But `users` carries RLS's standard tenant-scoped policy for any non-`platform_admin` row (the enable-RLS migration), and the app-layer `UserTenantScope` independently filters to `role = 'platform_admin'` only when no tenant context is set — so with no GUC set yet (nothing has set one at that point in the pipeline), `auth`'s own `SessionGuard::user()` lookup finds nothing for an owner or staff session, and the request is treated as a guest. `platform_admin` was never affected — RLS's widened `users` policy makes that role's own row visible unconditionally, regardless of GUC state — which is exactly why this went undetected: the admin path (Session 10) and every Pest test for the owner/staff paths (built behind the identical broken ordering) never actually exercised a **second**, separate HTTP request reusing a session cookie the way a real browser or a real `curl` session does. Pest's own test-transaction behavior (D-0025: a nested `TenantContext::run()`'s `set_config(..., true)` doesn't reset at a savepoint release, only at the outermost transaction's real commit) left the DB-level GUC set for the rest of any test that had called `TenantContext::run()` even once — masking the gap completely. Found only by executing a real login followed by a real second request against a live server for the first time this session.
- **Two fix candidates tried and rejected before the one that worked, both confirmed by execution, not reasoned away in the abstract:**
  1. **Bypass `UserTenantScope` alone** for the guard's `retrieveById()` lookup (a custom user provider) — built, tested, still 401'd. Confirmed by direct query that Postgres's own `FORCE ROW LEVEL SECURITY` on `users` blocks the row independently of the app-layer scope; an app-layer-only fix cannot work while RLS itself still says no.
  2. **Reorder the route array** — `resolve.tenant.from-session -> tenant.context -> auth -> role`, sourcing `tenant_id` from the session instead of the user row — the semantically correct fix, but Laravel's own request pipeline doesn't honor a route's literal middleware array order for any middleware that appears in its global `$middlewarePriority` list (framework-internal, unrelated to what any given route specifies): `Illuminate\Auth\Middleware\Authenticate` implements `AuthenticatesRequests`, which **is** in that list, so `SortedMiddleware` silently moved `auth` back to the front regardless of the array order written. Extending the priority list to compensate (`prependToPriorityList`) was tried and confirmed, by execution, to have non-local side effects on unrelated routes (Sanctum's own nested stateful-group pipeline resorts against the same global list, and pulled `tenant.context` ahead of `resolve.tenant.slug` on the public login route, breaking it).
- **Decision — one consolidated middleware, `App\Http\Middleware\AuthenticateTenantUser`, aliased `auth.tenant`, replacing the four-step pipeline with one step:** reads `tenant_id` from the Laravel session (not from the not-yet-resolved user row), fails closed `401 UNAUTHENTICATED` if absent or if there's no session store at all (an unauthenticated non-stateful request), opens `TenantContext::run($tenantId, ...)`, and *inside* that scope calls `Auth::guard('web')->check()`. Because everything happens inside one middleware's own `handle()`, there is nothing left for the framework's cross-middleware priority sort to reorder incorrectly. `AuthController::login()` now writes `tenant_id` into the session at the one point it's already legitimately known (that request runs behind `resolve.tenant.slug`) — reading it back later is exactly as trustworthy as `Auth::id()` already is: both are server-side session data, immune to client tampering, protected by the same encrypted/signed session cookie. **No new RLS-bypass surface is introduced** — D-0009's "exactly one bypass surface (`bookslot_migrator`), never live-reachable" invariant is unchanged; `platform_admin`'s separate `auth -> role -> resolve.tenant.impersonate -> tenant.context` pipeline is untouched (it was never affected).
- **Validated by execution, real server, twice over:** a full real login → `GET /api/owner/appointments` → `PATCH .../status` → invalid-transition round trip, once with `SESSION_DRIVER=redis` and once with `SESSION_DRIVER=file`, both succeeding identically — ruling out the local Redis/predis setup (D-0041's own local-environment note) as a contributing factor, isolating the bug to the middleware-ordering issue this decision fixes. `composer ci:check` green afterward (76/76 Pest tests, including every owner/staff/admin auth test already in the suite — none regressed).
- **What this means for every prior session's owner/staff verification:** Sessions 9–10's `StaffAppointmentControllerTest`/owner-service tests, and this session's own new `OwnerAppointmentControllerTest`, all passed throughout — correctly proving the *authorization logic* (role gating, tenant scoping of results) is right, but none of them, until this session's live-server pass, actually proved a returning session could re-authenticate at all outside Pest's own transaction-masking behavior. Recorded here so a future session doesn't read "Pest passes" as "production-proven" for this specific property again.
- **Must not be silently reversed because:** reverting to a separate `resolve.tenant.*`/`tenant.context`/`auth` step sequence for owner/staff routes — even a correctly-ordered one — reopens exactly the framework-priority-sort trap this decision found and fixed by execution, not by inspection; a future "obvious" refactor back to separate middleware steps must re-discover (or re-read) this entry first.

## D-0047 — A real RabbitMQ broker, not Redis, becomes this project's queue transport

- **Date:** 2026-09-13 · **Status:** accepted
- **Context:** `app/Jobs/TenantScopedJob`/`PlatformJob` and the `SetsTenantContext` job middleware (D-0009, Session 8) have existed since the first implementation session, but zero concrete job classes were ever built on top of them — nothing in this codebase had ever actually been queued. `.env.example` named Redis/Horizon as the intended queue transport (a Session-8-era comment, never executed on), but this session's own work order calls for a real broker specifically, not Laravel's Redis queue driver, as a genuine architectural addition distinguishing this project from the rest of this developer's portfolio.
- **Options considered:**
  (a) Laravel's built-in `redis` queue connection (already configured, zero new code) — rejected as not meeting the actual goal: it demonstrates Laravel's own queue abstraction, not message-queue architecture as its own subject (no real exchange/routing/dead-lettering concepts involved).
  (b) A third-party Laravel-RabbitMQ Composer package (e.g. `vladimir-yuldashev/laravel-queue-rabbitmq`) — rejected: it would hide exactly the mechanics (delayed delivery via dead-lettering, retry/attempt tracking, connector registration) this decision exists to make a real, readable part of this codebase rather than a dependency's internal, unexamined behavior; it also introduces a real risk of version-compatibility drift against this project's own Laravel version that this codebase would have no way to fix if the package's own maintenance lagged.
  (c) **Chosen:** a from-first-principles integration directly against `php-amqplib/php-amqplib` (a mature, actively maintained, framework-agnostic pure-PHP AMQP 0-9-1 client with no Laravel-version coupling) — `App\Queue\RabbitMq\RabbitMqConnector`/`RabbitMqQueue`/`RabbitMqJob`, registered via `Queue::extend('rabbitmq', ...)` in `AppServiceProvider::boot()`, resolved through Laravel's own `ConnectorInterface`/`Queue` contracts exactly the way `redis`/`database`/`sqs` are internally — so `QUEUE_CONNECTION=rabbitmq` and every existing `TenantScopedJob`/`PlatformJob` subclass work unmodified; nothing about D-0009's tenant-context middleware changes because the transport underneath it changed.
- **Delayed delivery — the one real architectural decision this integration required, since RabbitMQ core has no native delayed-message primitive:** the standard **TTL + dead-letter-exchange (DLX) pattern**. Each queue `{queue}` gets a paired `{queue}.delay` queue, never consumed directly, whose `x-dead-letter-exchange`/`x-dead-letter-routing-key` arguments route an expired message back to the default exchange with `{queue}` as the routing key — which, on the default exchange, IS an implicit binding straight to that queue. A delayed publish sets the message's own `expiration` property (milliseconds) rather than declaring a new queue per distinct delay value.
- **The one stated, accepted limitation of that pattern — named, not discovered by an incident:** RabbitMQ only expires a per-message TTL in head-of-queue order. A short delay published after a much longer one already sitting at the head of the same `{queue}.delay` queue will not dead-letter ahead of it — it waits behind the longer-delayed message's own expiry (or removal) first. At this project's actual traffic shape (a hold-window expiry and a handful of reminder touchpoints per booking, not a high-volume mixed-delay workload), this is an acceptable, explicitly accepted tradeoff, the same category of decision as D-0036's Stripe descoping and D-0011's provisional hold-window number — not a hidden gap.
- **Retry/attempt tracking — deliberately NOT RabbitMQ's own `x-death` header array:** `x-death`'s `count` field conflates every reason a message was ever dead-lettered (this project uses dead-lettering for BOTH the delay mechanism above AND retries), so it cannot cleanly answer "how many times has this exact job been attempted." `RabbitMqQueue`/`RabbitMqJob` instead manage an explicit `x-bookslot-attempt` message header themselves, incremented only on `release()`, read by `attempts()` — this is what lets Laravel's own unmodified `CallQueuedHandler` max-tries/backoff logic keep working correctly against this transport.
- **Testing strategy, extending `07-testing-strategy.md`'s existing tiers:** a new `queue-broker` Pest group (`composer test:queue-broker`), excluded from the fast gate (`composer test:fast`) the same way `slow` already is — real publish/consume/delay/retry proof against an actual RabbitMQ instance (`docker-compose.yml`'s `rabbitmq` service locally; a `rabbitmq` service container in `.github/workflows/ci.yml`), each test spawning a genuinely separate `php artisan queue:work --once` OS process to consume, mirroring `BookingConcurrencyTest`'s (D-0030) existing standard of proving a concurrency/transport property against real separate-process execution rather than an in-process assumption.
- **Must not be silently reversed because:** a future session switching `QUEUE_CONNECTION` back to `redis` "for simplicity" would silently discard this decision's entire point (a real broker with real delayed-delivery/dead-lettering semantics as a deliberate portfolio architecture choice) without recording why — if that tradeoff is ever worth making, it needs its own decision entry, not a quiet `.env` edit. Similarly, replacing the `x-bookslot-attempt` header mechanism with raw `x-death` counting would silently reintroduce the exact conflated-count bug this entry explains why it was avoided.

## D-0053 — Session 22: `charge.dispute.created`'s tenant-resolution gap (D-0048) closed — resolve via the Dispute's own `payment_intent`, a per-tenant RLS-respecting scan, never a metadata read that doesn't exist

- **Date:** 2026-09-16 · **Status:** accepted
- **Context, verified against real state before writing anything:** D-0048 (Session 19) built real Stripe webhook handling but explicitly named one gap rather than silently working around it: a Stripe **Dispute** (`charge.dispute.created`/`.closed`'s `data.object`) is a distinct Stripe object from the Charge or PaymentIntent it was raised against, and Stripe does not copy either's `metadata` onto it — so `StripeWebhookController`'s `metadata.tenant_id` read (the mechanism every other handled event type uses) always comes back empty for a dispute. - **Date:** 2026-09-16 · **Status:** accepted

- **Scope, decided and separated explicitly per the task's own instruction not to assume export and erasure are one operation:**
  1. **Export: a read-only, owner-triggered dump.** Genuinely low-risk (no mutation, no irreversibility) — the only real design question was *what* counts as this customer's own data (see `05`'s endpoint 11 section for the full per-field reasoning: `payments`/`refunds` minus Stripe IDs, `payment_mandates` minus Stripe IDs but otherwise in full, `booking_events` scoped to the customer's own appointments and trimmed to non-operational fields). - **The one genuinely new decision this session had to make — eligibility, not policy:** nothing in `04`/`06`/`09` ever addressed whether an in-flight booking should block erasure; D-0022 only ever addressed *what survives* an erasure that's already happening. Three options considered:
  - **Unconditional allow (anonymize regardless of booking state) — rejected.** A customer with a `confirmed` or still-`pending_payment` appointment for tomorrow still needs to be reachable and identifiable by the studio to actually deliver that appointment — reminders (`notification_deliveries`) need a real name/contact, and day-of staff need to know who's arriving. Silently anonymizing that customer out from under a live booking would degrade real service delivery, a genuine operational cost this decision should not create by default.
  - **Unconditional cascade-block (reject erasure whenever *any* appointment, however old, exists) — rejected.** This would make erasure practically unreachable for almost any real customer (most customers who ever booked have at least one historical appointment) and has no privacy-rights justification — a data-protection erasure right is not supposed to be defeated by the mere existence of old, already-resolved history the anonymize-in-place design already handles safely.
  - **Block only on a still-live booking (`pending_payment`/`confirmed`); anonymize-and-preserve for everything else — chosen.** This is the narrowest rule that actually protects the one real operational conflict (an upcoming appointment needing a reachable customer) without over-blocking on settled history. `completed`/`no_show`/`cancelled` appointments never block erasure — they're exactly the "historical, preserved via anonymize-in-place" case FR-18/D-0022 already designed for.
- **Idempotent, not `409`-on-repeat.** A second erasure call on an already-erased customer returns the current state as a `200`, not an error — matching D-0021's existing "retry is a safe no-op" discipline for `confirm-payment` rather than the "second call is rejected" discipline `refund()`/cancel() use for genuinely one-shot financial/status transitions. Chosen because erasure is not a financial transition with a meaningful "already happened, and a second attempt would double-apply" risk the way a refund is — a repeat erasure attempt (lost response, an owner double-clicking a UI button that doesn't yet exist) should never surface as a confusing failure for an action that already fully succeeded. Verified the repeat call does not re-randomize the synthetic anonymized email or write a second `customer_erased` event.
- **`booking_events.appointment_id: null` for the erasure event, not one row per affected appointment.** `04-data-model.md`'s own column note for `booking_events.appointment_id` already documents this exact case ("null for ... an event not tied to one appointment lifecycle transition") — no schema change needed. A customer-level PII change is not any one appointment's status transition, so recording it against every historical appointment would conflate two different kinds of audit fact (this appointment's own lifecycle vs. this customer's own data having been anonymized) in the same trail. This is the first `booking_events` row this codebase has ever written with a null `appointment_id` — every prior write (refund, balance charge, cancellation, status change, Connect webhooks) had a real appointment or, for Connect, was judged (D-0058) not to need a `booking_events` row at all.

  - **`booking`** (`POST /api/tenants/{slug}/bookings`): keyed on (IP + tenant slug) rather than IP alone — this is a per-tenant resource (a specific studio's calendar and Stripe Connect account absorb the abuse), so one IP's activity against tenant A must never throttle that same IP's unrelated, legitimate attempt against tenant B a moment later. Two tiers (per-minute burst, per-hour sustained-drip) mirroring the login limiter's own shape. Applied as `throttle:booking` ahead of `resolve.tenant.slug` on the route (`routes/api.php`) — a throttled request never pays for a tenant lookup, and the `{slug}` route parameter the limiter's own keying closure reads is already bound by Laravel's router before any route middleware runs, so ordering here costs nothing.
- **Thresholds calibrated against this repo's own real usage, not picked from a generic guideline and left unverified:** a stock Fortify-style 5/minute login limit and a naive 5/minute booking limit were each checked directly against this project's real, passing Playwright E2E suite (`frontend/tests/e2e/`, real HTTP, real Postgres/Redis, `workers: 1` sequential) before being finalized — that suite re-authenticates the one seeded `owner@demo-studio.test` credential roughly 9 times and creates roughly 6-7 real bookings against the one seeded `demo-studio` tenant, all from the same loopback IP, across its four spec files in a single run against one real, persistent (Redis-backed in a real dev environment) cache. A tighter, "textbook" threshold would have made that suite intermittently 429 partway through with no real code bug involved — caught by actually running the full suite against the new middleware (not just the backend Pest gate) before finalizing the numbers, per this project's own "verify a change by running it, don't assume" discipline. Final values (10/minute + 30/minute for login; 10/minute + 50/hour for booking) keep meaningful abuse protection — a scripted attacker is still capped at 10 requests/minute against either surface — while giving real headroom above the suite's own legitimate reuse pattern. Confirmed: the full Playwright suite (10/10) passes unchanged against the new middleware; the backend fast gate gained 6 new dedicated tests (`tests/Feature/Api/RateLimitingTest.php`) and lost none.
- **Response shape: `429 {"error": "TOO_MANY_REQUESTS"}`, matching this codebase's existing hand-mapped-exception convention (`bootstrap/app.php`), not Laravel's default `{"message": "Too Many Attempts."}`.** A new `ThrottleRequestsException` render callback added alongside the existing `ValidationException`/`NotFoundHttpException`/`AuthenticationException` ones; `$e->getHeaders()` is passed through so the `Retry-After` header `ThrottleRequestsException` already computes reaches the client unchanged.
- **`throttle:booking` runs before request validation, deliberately — a request counts against the limit whether or not its body is well-formed.** Verified directly by testing with an empty/invalid booking body (see `RateLimitingTest.php`): the limiter must protect against a flood of even-malformed requests, not just well-formed ones that reach the controller.
- **What this doesn't do, named rather than left implicit:** no rate limiting was added to any other endpoint (availability lookup, mandate display, confirm-payment, manage-booking read/cancel, any owner/staff/admin route) — none of those were named by this session's task, none trigger a paid external call per request the way booking creation does, and owner/staff/admin routes already sit behind session auth, a materially different threat model than an anonymous public endpoint. Extending rate limiting to any of those is a distinct, not-yet-made decision for a future session, not silently implied by this one.
- **Must not be silently reversed because:** lowering the booking/login thresholds back toward a "textbook" value without re-running the real Playwright suite would silently reintroduce exactly the false-429 flakiness this decision found and avoided by executing the check, not assuming the numbers were safe. Keying the booking limiter on IP alone (dropping the tenant-slug half of the key) would reintroduce unrelated cross-tenant throttling this decision specifically designed against. Removing the `ThrottleRequestsException` render callback "for simplicity" would silently regress every throttled endpoint's error shape back to Laravel's default, breaking `05-api-contracts.md`'s "one error-code convention for every `api/*` endpoint" property this file and `bootstrap/app.php` otherwise maintain everywhere else.

## D-0064 — Session 37: `manage_booking` token expiry — anchored to the appointment's own end time, not booking-creation time; no migration needed for already-issued tokens

- **Date:** 2026-09-19 · **Status:** accepted
- **Context:** D-0052 (Session 21) named an explicit, accepted residual risk rather than an oversight: `manage_booking` tokens are minted with `expires_at = null` — good for the lifetime of the booking, however far in the future, so a leaked link (a forwarded email, shared-device browser history) remains a live read/cancel credential indefinitely. This session's task named it as real, unresolved design debt worth closing with a considered decision, not a blanket short expiry that would break already-issued links.
- **Why not a fixed offset from issuance, the shape `confirm_payment`'s own token already uses (D-0021):** `confirm_payment` can afford a short, fixed window because its whole job is done within one hold window (`booking.hold_window_minutes` + a small grace, ~20 minutes by default) — the token is dead well before the appointment itself even happens. `manage_booking` has no equivalent natural deadline at issuance time: a booking can be made up to `booking.availability_max_lookahead_days` (60) in the future, and the customer's own real, undisputed need to view or cancel that specific booking persists right up until the appointment happens. A fixed offset from issuance would either have to be at least 60+ days (barely improving on "no expiry" for a near-term booking, since most bookings are made far closer to their date than the lookahead ceiling) or would silently invalidate a distant-future booking's own management link before the appointment it's for ever occurs — actively worse than the status quo for exactly the customers who most need a working link (the ones who booked furthest ahead).
- **Decision: anchor the expiry to the appointment's own `ends_at` instead, plus a fixed grace period after — `ends_at + config('booking.manage_booking_token_expiry_grace_days')` (default 3 days), computed once at issuance in `BookingController::store()`.** This is the same anchor-plus-grace *shape* `confirm_payment`'s token already uses, just anchored to a different, appointment-relative event rather than booking-creation time — not a new mechanism invented for this token, a natural extension of the one D-0021 already established. 3 days covers late self-service cancellation and a short post-appointment lookup window (a receipt-like use — the same `GET .../manage/{token}` read this token has always supported) without leaving the link live indefinitely; an explicit, reasoned provisional guess, the same status this project already gives `hold_window_minutes`, not validated against real usage (no real pilot exists yet, R-01).
- **No migration, no backfill, no forced-invalidation step for already-issued tokens — and this is not an incomplete implementation, it's the only technically honest option `SignedTenantToken`'s own design (D-0021) allows.** The class is deliberately stateless: no storage, no revocation, verification is signature + claims only. A token's `expires_at` claim is baked into its own encrypted payload at the moment `SignedTenantToken::issue()` is called and can never be changed after the fact by any later code or config change — there is no row anywhere to update. Concretely: every `manage_booking` token issued before this change carries `expires_at: null` in its ciphertext and keeps resolving exactly as it always has, forever (`SignedTenantToken::verify()`'s expiry check is unconditionally a no-op when `expires_at` is null — unchanged code, not a new carve-out). Every booking created from this change onward gets the new bounded expiry. The population of never-expiring links shrinks to zero on its own as those older bookings' appointments complete and their tokens simply stop being used, rather than needing an explicit, riskier "expire everyone's existing link on a cutover date" step that would break real, already-sent links with no way to warn their holders first.
- **Scope, checked explicitly against what this decision does and does not touch:** `confirm_payment`'s own expiry (D-0021, unchanged) is untouched — this decision only changes what `BookingController::store()` passes as the fourth argument to `SignedTenantToken::issue('manage_booking', ...)`; `ManageBookingController::show()`/`cancel()` and `SignedTenantToken::verify()` needed zero code changes, since the expiry check they already run was always ready for a non-null `expires_at`, just never given one for this purpose until now. D-0052's own cancellation-eligibility logic (`CANCELLABLE_STATUSES`) is unrelated and unchanged — a token can still resolve a terminal (`completed`/`cancelled`/`no_show`) appointment for read purposes right up until its own new expiry, same as before; only the token's own lifetime is bounded now, not what states it can act on.
- **Tested:** `tests/Feature/Api/BookingControllerTest.php` — a new end-to-end test creates a real booking, computes the expected `ends_at + grace_days` boundary from the appointment's own real `ends_at`, then uses `travelTo()` to prove the returned `manage_token` still resolves the instant before that boundary and is rejected (generic `404 INVALID_OR_EXPIRED_TOKEN`, no distinct code) the instant after. `tests/Feature/Api/ManageBookingControllerTest.php` — a new dedicated regression test mints a token the old way (no fourth argument, reproducing the exact pre-D-0064 shape) and travels 5 years into the future to prove it still resolves, guarding the backward-compatibility claim above against a future session accidentally tightening `SignedTenantToken::verify()` in a way that would silently break every link issued before this change.
- **Must not be silently reversed because:** switching `manage_booking`'s anchor from `ends_at` back to booking-creation time "for consistency with `confirm_payment`" would reintroduce the exact distant-future-booking failure mode this decision exists to avoid — the two tokens have deliberately different anchors because they serve genuinely different-duration purposes, not by inconsistency. Adding a revocation/storage mechanism to `SignedTenantToken` "to also invalidate old null-expiry tokens immediately" would be new, unrequested scope reopening D-0021's explicit no-storage decision, and would need its own dedicated design pass (keying, cache invalidation, cross-token-purpose blast radius) rather than being bolted onto this one.

## D-0065 — Session 38: Stripe Connect account-replacement after deauthorization — `account.application.deauthorized` now clears the stale account id and marks a distinct `deauthorized` status, so the existing onboarding-link endpoint naturally reconnects a fresh account

- **Date:** 2026-09-19 · **Status:** accepted
- **Context, verified against real state before writing anything:** `12-session-handoff.md`'s Session 37 amendment (latest at session start) still named "no Connect account-replacement flow after a deauthorized account (D-0058)" as unchanged backlog — the same gap D-0058 (Session 28) itself named and deliberately declined to build: "building 'detect deauthorization, then let the owner connect a *different* Stripe account' would be new, undesigned product behavior, not a natural extension of onboarding-link generation." This session is exactly that follow-up, chartered to actually design and build it. Read in full before proposing anything: D-0058's complete entry (above), `04-data-model.md`'s `tenants` table, `Owner\StripeConnectController`, `ConnectOnboardingGateway`/`StripeConnectOnboardingGateway`/`FakeConnectOnboardingGateway`, `ProcessStripeWebhookJob`'s `handleAccountUpdated()`/`handleAccountDeauthorized()`, and `StripeWebhookController`'s Connect-event tenant-resolution branch.
- **Scoping question 1, resolved by tracing the real code, not assumed either way: does `onboardingLink()` already support reconnection if called again post-deauthorization? No — it actively breaks it.** `onboardingLink()` (`app/Http/Controllers/Api/Owner/StripeConnectController.php`) only calls `createAccount()` when `tenant->stripe_connect_account_id === null`; D-0058 deliberately left that column populated with the old, now-inaccessible account id after deauthorization ("a true historical record"). Calling the endpoint again therefore skips account creation entirely and calls `createAccountLink()` against the dead account id — which a real Stripe account-links call for an account the platform's connection to has been revoked can only fail (a 502 `PAYMENT_PROVIDER_UNAVAILABLE`, indistinguishable from a transient outage, with no code path that ever recovers from it). The same stale id would make `status()`'s live `retrieveAccountStatus()` call fail identically. So the two routes D-0058 built are not just unhelpful post-deauthorization, they are actively broken — a real, previously-unnoticed regression this task's own investigation surfaced, not a hypothetical.
- **Decision: clear `stripe_connect_account_id` back to null in `handleAccountDeauthorized()`, and mark the tenant a new, distinct `deauthorized` status (not `restricted`) instead.** This is the "minimal correct fix" the task's own framing pointed at: once the column is null, `onboardingLink()`'s existing "create an account if missing" branch is *already* the entire reconnection mechanism — no new endpoint, no new controller method, no new frontend route. The only genuinely new code is the CHECK-constraint migration adding `deauthorized` as a fifth allowed value (same drop-and-recreate pattern as `2026_08_25_000019_add_platform_admin_to_booking_events_actor_type.php`), the two-line change to `handleAccountDeauthorized()` itself, and a one-line change to `status()`'s existing null-account-id short-circuit so it reports `deauthorized` (not a bare `not_started`) when that's the tenant's last recorded status.
- **Why `deauthorized` needs to be its own status value, not reused `restricted` (this session's scoping question 2, on the UI side):** `restricted` already means something specific and still-actionable — Stripe has flagged a *still-connected* account (e.g. mid risk-review), and the fix is to follow the same account's own hosted flow to submit whatever Stripe still needs; the account id is still valid and a fresh Account Link genuinely helps. `deauthorized` means the platform's access to that account is gone entirely — the fix is to connect a *different* account, an operation that looks identical at the API-call level (the same `onboardingLink()` POST) but means something materially different to the owner reading the settings page. Collapsing both into one `restricted` value (D-0058's original design, made before this reconnection flow existed to need the distinction) is exactly what would leave a deauthorized owner reading "Stripe has flagged this account, follow the link to see what Stripe needs" — actively misleading, since there is no "this account" left to fix. `Owner\StripeConnectController::status()`'s null-account-id branch is the one place this distinction has to be preserved, since clearing the account id would otherwise make a `deauthorized` tenant indistinguishable from one that never onboarded at all (bare `not_started`), erasing exactly the history the owner-admin UI needs to show a "reconnect" message instead of a first-time "get started" one.
- **A second, independent correctness gap this investigation found and closed — a stale/out-of-order `account.updated` webhook overwriting a tenant's post-reconnection status.** `account.updated` resolves its tenant via the Stripe Account object's own persisted `metadata.tenant_id` (`StripeWebhookController`), which — unlike `stripe_connect_account_id` — is not cleared by deauthorization and survives on the old, disconnected Account object indefinitely. If a late-arriving `account.updated` for that *old* account were ever delivered after the tenant had already reconnected a brand new account (a new id, by then written to `stripe_connect_account_id`), `handleAccountUpdated()` would previously have applied the old account's stale `charges_enabled`/`details_submitted`/`disabled_reason` fields directly onto the tenant's *current* status — a real, if narrow, race in the exact gap this task asked about ("what happens to ... state tied to the old account during the gap between deauthorization and reconnection"). Fixed by comparing the event's own `data.object.id` (which account this specific event is actually about) against the tenant's current `stripe_connect_account_id` before applying anything, skipping and logging a mismatch instead. Deliberately not built as a generic event-ordering/sequencing mechanism — a single equality check against the one column that already tracks "which account is current" is sufficient and proportionate to the actual risk; Stripe Connect webhooks are not expected to keep arriving for a fully disconnected account in practice, so this is defense-in-depth for an unlikely-but-real ordering edge, not a load-bearing mechanism this design depends on.
- **What happens to already-settled payment/refund rows tied to the old account — checked, no gap found, nothing changed.** `payments`/`refunds` store their own `stripe_payment_intent_id`/`stripe_refund_id` at the time each Stripe call succeeds; neither table holds a live reference to the tenant's *current* `stripe_connect_account_id` that clearing it could retroactively corrupt. A `completed`/`succeeded` payment made against the old, now-deauthorized account remains exactly as historically accurate after this change as before it — this decision touches no code in `Owner\AppointmentController::refund()`/`chargeBalance()`, `Payment`, or `Refund`, per this task's own explicit instruction not to.
- **What happens to a *new* refund/balance-charge attempt made during the gap (deauthorized, not yet reconnected) — a real, named residual gap, deliberately left unfixed here per this task's own DO NOT list, not overlooked.** `refund()`/`chargeBalance()` pass `tenant->stripe_connect_account_id` straight through to `PaymentIntentGateway::refund()`/`chargeOffSession()` with no null-check beforehand; `StripePaymentIntentGateway`'s own `create()`/`chargeOffSession()` already treat a null connected-account id as "omit `transfer_data`/`application_fee_amount` entirely" (checked directly — this is pre-existing behavior, unchanged by this session, and is exactly what already happens today for any tenant that has never completed onboarding at all, `stripe_connect_account_id` having been null from `not_started` the whole time). So a balance-charge or refund attempted mid-gap does not error — it silently succeeds against the *platform's own* Stripe account, with no destination transfer and no application fee, identical to the pre-existing never-onboarded-tenant case. This is consistent, not a new regression this session introduces, but is worth a future session's attention if real money ever needs to be reconciled back to a studio for charges made while disconnected — out of scope here per this task's explicit "do not touch refund/balance-charge logic" instruction, flagged rather than silently left for someone to rediscover.
- **Owner-admin UI (Session 36, D-0062):** `frontend/app/pages/owner/settings/stripe/index.vue` needed a `deauthorized` case in its `statusLabels`/`actionLabel` maps and one new inline warning paragraph — the underlying button still calls the exact same `POST .../onboarding-link` action for every non-`not_started` status (D-0058's "one action serves start/resume/refresh/reconnect" design holds unchanged); only the label ("Connect a new Stripe account" instead of "Continue onboarding with Stripe") and the explanatory copy (clarifying that reconnecting doesn't affect past bookings/payment history) differ. `frontend/app/types/owner.ts`'s `ConnectStatus['status']` union gained the new value.

Full fast gate and `queue-broker` group re-run clean; `npx vue-tsc --noEmit`/`npx vitest run` clean for the frontend change.

Adding a generic webhook-event-sequencing/ordering framework instead of the single-column equality guard in `handleAccountUpdated()` would be solving a problem broader than what this codebase actually has evidence of needing.
